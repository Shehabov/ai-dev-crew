# BUGS.md

The defect register. Every defect found in this product, and every mistake an agent makes
while building it, is recorded here so it is not made a second time.

`bug-historian` owns this file and is the only agent that writes to it. It reads the
register at the start of every run and briefs the team on what has already gone wrong on
the surfaces the change touches.

If you are an agent starting work, read the entries tagged with the surface or component
you are about to change, and every standing rule, before you plan. A defect that repeats is
worse than a new one, because it means the register was written and nobody read it.

---

## How to use this file

| You are | Do this |
|---|---|
| The Product Lead | Raise anything. One line is enough. `bug-historian` fills in the rest. |
| `qc-engineer` or `qc-lead` | Record the defect in the run, in `qc-engineer/defects.md` or `qc-lead/readiness.md`, with reproduction steps and the evidence path. `bug-historian` carries it here at its record pass. |
| Any other agent | Do not edit this file. Report the defect in your handoff, under `blockers` or `machinery_findings`, and `bug-historian` records it. |
| Any agent starting a run | Read it. Filter by surface and by agent. Carry the relevant entries and every standing rule into the audit step of your plan. |

## Entry format

Every entry is one block. Ids run in sequence from `BUG-0001` and are never reused. An entry
is never deleted: it closes, and it stays.

The example below is illustrative. It shows the shape and the level of detail, and is not
a defect in this product.

```markdown
### BUG-NNNN · An access error named the invoice it refused

| | |
|---|---|
| Status | closed |
| Raised by | qc-engineer |
| Raised on | 2026-10-01 |
| Run | 2026-10-01-invoice-export |
| Surface | api/invoices |
| Component | the invoice export function |
| Agent at fault | backend-engineer |
| Class | invariant |
| Severity | blocker |
| Evidence | `.devteam/runs/2026-10-01-invoice-export/evidence/i1-error-path.log` |
| Fixed in | `fix/export-error-body`, closed 2026-10-02 |
| Repeat of | none |

**What happened.** Asked for an invoice from another account, the export refused the
request, and the error body carried that invoice's number and the other account's name.

**Why it got through.** The invariant was tested on the data path and not on the error
path. The test asserted that the request was refused, not what the refusal said.

**The rule this produces.** An error raised by an invariant names the rule that refused,
never the input that tripped it. Applies to every invariant, not only this one.

**Who must be briefed.** backend-engineer, security-analyst, code-analyst, qc-engineer.

**How to detect it next time.** Stack: SQL and TypeScript. For every function that raises
an access error, read the message and hint arguments: none may interpolate an id, a name or
a count from the refused row. Seen to fire on the unfixed function before the fix.
```

### Fields that matter

| Field | Why |
|---|---|
| `Status` | `open` or `closed`. Nothing else, so the Open index below can be counted. |
| `Agent at fault` | It routes the next run's brief to the right agent, and assigns no blame. Where the fault is in a brief, a spec or an agent file rather than in the implementation, say so. Where no agent is at fault, write `none` and route the entry through "Who must be briefed". |
| `Class` | One of the classes below. It is what makes the register searchable. |
| `Severity` | `blocker` stops the run or breaks an invariant. `major` is wrong behaviour a user or an agent will meet. `minor` is wrong but contained. |
| `Repeat of` | If the same pattern happened before, the earlier id. A repeat is a process failure, and a third occurrence escalates to the Product Lead. |
| The rule this produces | The general lesson, stated so it applies beyond the one incident. A rule that binds beyond one entry becomes a standing rule. |
| How to detect it next time | A concrete check, ideally a command, with the stack or tool it needs. It is run on the unfixed state and seen to fire before the entry closes. |

---

## Classes

| Class | Means |
|---|---|
| `invariant` | A rule in `PROJECT.md § Product invariants` broken or weakened. The most serious class. |
| `state-machine` | An illegal transition, or a state reached without the evidence its transition requires |
| `contract` | Two sides disagreed about a shape: the front end and the back end, or two agents |
| `correctness` | A plain bug: logic, null, boundary, time zone, race |
| `security` | Access control, injection, secrets, personal data in a log or a URL, a vulnerable dependency |
| `data-layer` | A query in a loop, a missing index, an unbounded query, a migration that locks or cannot be reversed |
| `brand` | A token, contrast, type, spacing, motion or copy rule from the brand spec broken |
| `design-system` | Shell, component anatomy, density, state coverage, a width that breaks |
| `locale` | A missing locale, right-to-left layout, length, plurals, a string built by joining words to a number |
| `accessibility` | Contrast, focus, target size, colour as the only carrier of meaning, screen reader support |
| `process` | A gate skipped, a handoff unread, a planned role not used, a rejection loop, one definition kept in two places |
| `agent-behaviour` | An agent did what it is told never to do: invented a value, claimed work without evidence, narrowed scope silently, added attribution |

## Standing rules

Standing rules bind every run. `bug-historian` briefs them at the start of every run that
touches the surfaces they name, and a standing rule outranks an agent's instinct.

The twelve seed rules below ship with the team. They come from mistakes that recur on any
project, whatever its stack. Rules produced by this project's own closed entries are added
after them, from `SR-13` onward, each naming the entry it came from.

| # | Rule | From | Binds |
|---|---|---|---|
| SR-01 | Evidence is a file, never a claim | seed | every agent |
| SR-02 | Timestamps come from the shell | seed | every agent |
| SR-03 | One source for every definition, never two copies | seed | tech-architect, orchestrator, any agent defining a shared format |
| SR-04 | A count is derived from the list it counts | seed | every agent, bug-historian in particular |
| SR-05 | A fix reaches everywhere the defect lives, and its detection is seen to fire first | seed | every agent, bug-historian when it closes an entry |
| SR-06 | A checker never repairs what it checks | seed | orchestrator, bug-historian, the four reviewers, qc-lead |
| SR-07 | A handoff names its stage, and no pass overwrites another | seed | every agent |
| SR-08 | A gate is recorded only by its owner, under a name the plan carries | seed | every gate owner, orchestrator |
| SR-09 | A published command has been run | seed | every agent |
| SR-10 | A spec is read at the moment it is cited | seed | every agent |
| SR-11 | A reference image never sets a value | seed | ux-designer, ux-auditor, frontend-engineer |
| SR-12 | A spec that contradicts itself goes to the Product Lead | seed | every agent that reads the brand spec or `PROJECT.md` |

### SR-01 · Evidence is a file, never a claim

| | |
|---|---|
| Rule | A pass, a fix or a test result exists only as a non-empty file under the run's `evidence/` folder, or as a path in a handoff's `produced`. A sentence saying that something passed is a claim, and a claim is a blocker. |
| Why | Every gate reads files. A gate that accepts a sentence certifies whatever its author believed, and the next role inherits the belief as fact. |
| Detect a breach | For every handoff in the run, confirm that each `produced` path and each `gates[].evidence` path exists and is non-empty. `node .devteam/bin/utilisation-check.mjs <run-dir>` reports a missing or empty output as `PHANTOM_OUTPUT`. |

### SR-02 · Timestamps come from the shell

| | |
|---|---|
| Rule | Every time written into a handoff, a ledger line or a register entry is read from the shell at the moment it is written, with `date -u +%Y-%m-%dT%H:%M:%SZ`. Never typed from memory, never estimated, never copied from another record. |
| Why | The ledger's order is the only proof of which role ran before which gate passed. An invented time can place a dispatch on either side of the gate it waited for, and either way the record is false. |
| Detect a breach | Every `started` precedes its `finished`, and both fall between the run's `opened` time and the handoff file's modification time. The utilisation check reports reversed times as `NO_TIMING`. A run of round times, such as several handoffs finishing on the hour, is read as invented until shown otherwise. |

### SR-03 · One source for every definition, never two copies

| | |
|---|---|
| Rule | A schema, a vocabulary, a list of names, a format or a sequence is defined in one file, and every other file points to it. Where two files must carry the same text, such as the run plan template in `orchestrator.md` and in `team-orchestration`, a check proves the two are byte-identical. |
| Why | Two copies drift, and each reader follows whichever copy they opened first. Mismatched gate names, two ledger formats and two vocabularies for one finding are the same defect each time: one definition, written twice. |
| Detect a breach | For any shape or list of names that appears in more than one file, extract the keys or names from each copy and diff them. Any difference is a finding, and so is a second copy with no check holding it to the first. |

### SR-04 · A count is derived from the list it counts

| | |
|---|---|
| Rule | When a member joins or leaves an enumerated set (an agent, a gate, a skill, a locale, an invariant), every list of that set and every number written about it changes in the same edit. A number in prose is found by counting the list, never remembered. |
| Why | A gate added where it is used but not where it is counted leaves a plan that skips it. The same slip hides open defects when this register's own index is written from memory. |
| Detect a breach | Count the canonical list, then search the repository for a number followed by the set's noun, in words or digits ("twelve gates", "16 agents"), and confirm every hit agrees. For this file, the count of entries whose status reads `open` must equal the number of rows in the Open table; the command is under Open below. |

### SR-05 · A fix reaches everywhere the defect lives, and its detection is seen to fire first

| | |
|---|---|
| Rule | Before an entry closes, the whole repository is searched for the same value, pattern or wording, and every instance is fixed. The entry's detection command is run on the unfixed state first and must report the defect; a command that cannot fire is not a check. |
| Why | A fix made where the defect was noticed and missed thirty lines away is the same defect, still open. A detection that returns clean because it never reached the affected files reads as proof, which is worse than having no check at all. |
| Detect a breach | Run the detection before the fix, where it must fire, and after, where it must return nothing. Search recursively with `grep -r` or `git grep`, never through a `**` glob, which many shells expand only one folder deep. |

### SR-06 · A checker never repairs what it checks

| | |
|---|---|
| Rule | A script, a guard or a review that checks something reports what it finds and changes nothing it checks. Repair is a separate step, taken by the role that owns the thing checked, and the check runs again afterwards. |
| Why | A checker that quietly fixes what it inspects always reports clean, so its report proves nothing, and the author of the defect never learns it happened. The gate sync copies results and never decides one; the utilisation check reports and never edits a handoff; the four reviewers write findings and never edit the code. |
| Detect a breach | Read the check for writes. A check script that opens any file it inspects for writing is a breach, and so is a reviewer's handoff whose `produced` names a file under review. |

### SR-07 · A handoff names its stage, and no pass overwrites another

| | |
|---|---|
| Rule | Every handoff carries the `stage` of the plan entry it answers. An agent that runs more than once in a run writes `handoff.json` on its first pass, `handoff-stage<N>.json` on each later plan entry, and `handoff-stage<N>-round<R>.json` on a repeat pass at the same stage, such as a fix round. Any artefact an agent writes more than once in a run carries the pass in its name. |
| Why | bug-historian runs three times a run. When every pass wrote one path, the guard destroyed the brief's record, and every role that had read the brief appeared to claim it had read something that no longer existed. |
| Detect a breach | After any later pass, list the agent's run folder and confirm the first pass's handoff is still there. The utilisation check pairs handoffs to plan entries by stage and reports a pass with no handoff as `NEVER_RAN`. |

### SR-08 · A gate is recorded only by its owner, under a name the plan carries

| | |
|---|---|
| Rule | A gate result appears only in the `gates[]` of a handoff written by that gate's owner, under a gate name in the run plan's `gates[]`. Self-checks and sub-gates go in `review.md` or a verdict file. No role certifies another role's gate, and no role invents a gate name. |
| Why | A result recorded by the wrong role, or under a name the plan does not carry, cannot be enforced: nothing waits on it, and the stage it should have held starts anyway. |
| Detect a breach | `node .devteam/bin/sync-gates.mjs <run-dir>` refuses a result from a role that does not own the gate, and `node .devteam/bin/utilisation-check.mjs <run-dir>` reports `GATE_SELF_CERTIFIED` and `UNKNOWN_GATE`. |

### SR-09 · A published command has been run

| | |
|---|---|
| Rule | A command written into a skill, an agent file or a detection line in this register has been run at least once on the toolchain in `PROJECT.md § Toolchain`, and its output seen. A tool that section does not list as present is never assumed, and a step that needs it is reported as `blocked`. |
| Why | A check written to read correctly, rather than to run, looks like coverage and provides none. Commands get published in tools the machine does not have, and in shell forms that hang in the environment they were written for. |
| Detect a breach | Run every command in the changed file and save the output. Compare every tool each command names against `PROJECT.md § Toolchain`. |

### SR-10 · A spec is read at the moment it is cited

| | |
|---|---|
| Rule | A value, a section name or a rule taken from the brand spec, `PROJECT.md` or any other binding file is read from the file at the moment it is written down, never recalled. A value the spec does not contain is not used, even when it looks right: if the value you want is missing, the design is wrong. |
| Why | Section numbers and values drift in memory towards whatever seems plausible. A plausible citation of the wrong section, or a size between two steps of the scale, survives a casual read and fails the first real audit. |
| Detect a breach | For every citation in a changed file, open the cited file and confirm the section exists and says what the citation claims. For every design value, search the brand spec for it. |

### SR-11 · A reference image never sets a value

| | |
|---|---|
| Rule | Design references set structure: anatomy, density, hierarchy, interaction. Every colour, size, weight, radius and duration comes from the brand spec. A reference image cited as the source of a value is always a defect. |
| Why | A measurement taken from an image feels like evidence, and references carry their own palettes. A value read off a reference by eye enters the product as a second, unapproved palette. |
| Detect a breach | Search design documents for a hex, pixel or duration value in the same sentence or table row as a reference file name. Every such pairing is a finding. |

### SR-12 · A spec that contradicts itself goes to the Product Lead

| | |
|---|---|
| Rule | Before relying on a rule from a binding spec, search the same spec for every other section that governs the same token or concept. Where two sections disagree, report the contradiction to the Product Lead with options and a recommendation, and do not choose a reading alone. |
| Why | A condensed or amended spec often states one thing twice, differently. Each reader then builds a defensible and different answer, and the audit that follows cannot tell which was meant. |
| Detect a breach | Search the spec for the token or the concept's name and read every hit. Two rules for the same thing is a finding, and so is a handoff that relied on one of them without saying the other exists. |

start of every run.

|---|---|---|---|

None yet.

Two occurrences of a pattern make it a repeat. A third escalates to the Product Lead as a
process failure rather than a defect, because by then the register is plainly not being read.

| State | Means |
|---|---|
| `watching` | Two occurrences. Every regression brief on a surface the pattern touches carries it. |
| `escalated` | Three or more occurrences, with the decision now with the Product Lead. |
| `decided` | The Product Lead has chosen. The choice is quoted and dated in the standing rule's block, with the ledger line cited. |
